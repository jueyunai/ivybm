# 单一 production 部署手册

## 范围与边界

当前项目只有一个线上 production 环境：本地测试和 GitHub CI 是发布前质量门禁，1Panel 只负责手动拉取已发布的镜像并重建容器。本流程不使用常驻 staging、不允许服务器现场构建，也不配置自动硬盘快照或自动备份任务；每次 schema 发布前人工执行一次经过校验的 PostgreSQL SQL 与媒体文件备份，并复制到独立受控的离机位置。

无备份阶段禁止不可逆 migration，也不能将不可替代的客户数据写入生产数据库。应用镜像回滚不等于数据库回滚。**首次接收不可替代客户数据前，停止发布并先完成外部备份和恢复演练。**

## 发布前准备

1. 将经过 review 的提交合并到 `main`，确认 `CI` workflow 成功。
2. `Publish production images` workflow 会为该提交推送两份 SHA 标签镜像：
   - `ghcr.io/jueyunai/ivybm-runtime:<commit-sha>`
   - `ghcr.io/jueyunai/ivybm-worker:<commit-sha>`
   - workflow summary 会同时输出该 tag 对应的 runtime / worker **digest**。生产 `.env` 必须保存同一行输出中的 tag 和 digest；Compose 会用 `:<commit-sha>@sha256:…` 拉取，digest 才是实际不可变的发布引用。
3. 确认 GHCR package 保持 private，并在 1Panel 的部署端保存一个只带 `read:packages` 权限的拉取凭据。不要把该凭据写入仓库、GitHub Actions 日志或 Compose 文件。
4. 将经 review 的 `compose.yaml`、`compose.prod.yaml`、`docker/postgres/`、`scripts/production-compose.sh`、`scripts/preflight-production.sh`、`scripts/backup-production.sh`、`scripts/verify-production-backup.sh`、`scripts/restore-production-backup-check.sh` 和 `scripts/smoke-test.sh` 放入 1Panel 管理的部署目录，例如 `/opt/ivybm/`；这些文件来自已验证的提交，服务器不 clone、安装依赖或构建业务源码。

## DNS 与 1Panel 安全配置

在实际首次上线前，由域名管理员在阿里云添加以下记录，目标均为 `43.165.0.83`：

| 主机记录 | 类型  | 记录值        | 用途                     |
| -------- | ----- | ------------- | ------------------------ |
| `@`      | A     | `43.165.0.83` | 正式主站                 |
| `www`    | CNAME | `ivybm.com`   | 主站别名与 301 canonical |
| `panel`  | A     | `43.165.0.83` | 1Panel 管理入口          |

随后在 1Panel 中：

1. 为 `ivybm.com` / `www.ivybm.com` 配置 OpenResty 反向代理和 HTTPS，只转发到 `127.0.0.1:3000`。
2. 将面板绑定为 `panel.ivybm.com`，开启面板 TLS、安全入口和两步验证。面板继续使用独立端口（当前为 `8090`），不能占用 OpenResty 的 `443`。
3. 腾讯云防火墙只公开 `80` / `443`；当前面板端口只允许 `199.83.211.101`；删除公网 `22` 规则。域名绑定不能替代 IP 白名单。
4. 服务器控制通过腾讯云 Lighthouse MCP 完成，不需要开放 SSH。


`IMAGE_TAG` 和 `APP_VERSION` 必须同为本次发布的 40 字符 Git commit SHA；`RUNTIME_IMAGE_DIGEST` / `WORKER_IMAGE_DIGEST` 必须是该 SHA 在 workflow summary 中输出的 `sha256:` digest。`DATABASE_URL` 在 Compose 网络内必须使用 `db:5432`，不能使用宿主机 `127.0.0.1`。`NEXT_PUBLIC_SERVER_URL` 是在 CI 构建阶段写入 SEO、sitemap 和 robots 的正式 HTTPS 域名，必须是 `https://ivybm.com`。

`POSTGRES_PASSWORD` 至少 24 个字符，`PAYLOAD_SECRET` 至少 32 个字符。`TRUST_PROXY_HEADERS=true` 的前提是 OpenResty 是唯一应用入口，且会覆盖客户可伪造的转发 IP 头。禁止在 production `.env` 中添加 `SEED_ADMIN_EMAIL` 或 `SEED_ADMIN_PASSWORD`，也不要执行 demo seed。

`AI_CONFIG_ENCRYPTION_KEY` 是必填的 64 位十六进制服务器密钥，用于 AES-256-GCM 加密 CMS 内保存的供应商 API key。首次在服务器生成一次即可：`openssl rand -hex 32`。它只注入 app / worker，绝不写进 CMS、日志、审计记录、镜像或 Git；**不要在已有供应商凭据时随意更换**，否则旧凭据无法解密。

### Portal V1 首次生产启用方案（仅记录，未经授权不得执行）

Portal 与官网、Payload `/admin` 使用同一 runtime、worker 和 PostgreSQL。Portal V1 的一个 Draft PR 通过 review、最终 head 门禁并合并后，只计划执行一次人工 production 部署；合并或 CI 成功不会自动部署。`/admin` 在新版验收完成前继续保留，Portal 不提供跳转。

首次启用预期配置：

```text
ADMIN_PORTAL_ENABLED=true
ADMIN_PORTAL_SETTINGS_ENABLED=true
ADMIN_PORTAL_OVERVIEW_ENABLED=true
ADMIN_PORTAL_WEBSITE_CONTENT_ENABLED=true
ADMIN_PORTAL_MEDIA_ENABLED=true
ADMIN_PORTAL_KNOWLEDGE_ENABLED=true
ADMIN_PORTAL_CONVERSATIONS_ENABLED=true
ADMIN_PORTAL_LEADS_ENABLED=true
ADMIN_PORTAL_CONTENT_STUDIO_ENABLED=true
ADMIN_PORTAL_PLATFORMS_ENABLED=true
ADMIN_PORTAL_OPERATIONS_ENABLED=true
ADMIN_PORTAL_PUBLISHING_ENABLED=false
```

Portal 与官网、Payload `/admin` 共享同一应用。`ADMIN_PORTAL_ENABLED` 是 Portal 总开关；每个导航模块都必须在 production `.env` 中显式设置 `true` 或 `false`，缺失时 fail closed。`ADMIN_PORTAL_PUBLISHING_ENABLED` 是独立的外部发布 kill switch，本次必须保持 `false`。平台状态页可以启用，但真实发布必须保持关闭。本次发布不配置 `META_WEBHOOK_APP_SECRET`、`META_WEBHOOK_VERIFY_TOKEN`、`META_WEBHOOK_ALLOWED_ACCOUNT_IDS` 或任何真实平台 token。Meta/LinkedIn transport adapter、token 刷新、worker 发布 handler、平台回调、`delivery_unknown` 补偿和受控账号联调由 xuemusi 后续独立 PR 完成；现有 contract、请求构造器、Fake、readiness 和 Meta Webhook 基础代码不得描述为真实发布已完成。

`PLATFORM_CREDENTIAL_ENCRYPTION_KEY` 在首次把平台 access token 或 refresh token 保存到后台的“平台账号”前设置。它也是独立的 64 位十六进制密钥，可用 `openssl rand -hex 32` 生成；只注入 app / worker，不注入 migrate。当前没有平台账号令牌时可留空，但一旦已有加密令牌就**不能随意更换**，否则无法解密旧令牌。平台 App Secret、Client Secret 与 Meta webhook verify token 仍只保留在服务器 `.env`，绝不填入 CMS。

启用当前 Facebook Page OAuth 时，`META_APP_ID`、`META_LOGIN_CONFIG_ID`、`META_OAUTH_REDIRECT_URI` 与 `META_WEBHOOK_APP_SECRET` 必须同时配置，production 回调必须精确为 `https://ivybm.com/api/platforms/meta/oauth/callback`，并且 `PLATFORM_CREDENTIAL_ENCRYPTION_KEY` 不得为空。该配置不用于 Instagram；Instagram 需在独立授权配置和代码路径完成后另行启用。Meta App Secret 只注入 app；OAuth 配置 ID、回调和 App Secret 均不注入 migrate / worker。Webhook 的 App Secret、verify token 和账号 allowlist 仍按三项成组校验。

启用 Instagram Professional OAuth 时，`INSTAGRAM_APP_ID`、`INSTAGRAM_APP_SECRET`、`INSTAGRAM_OAUTH_REDIRECT_URI` 与 `PLATFORM_CREDENTIAL_ENCRYPTION_KEY` 也必须同时配置，production 回调必须精确为 `https://ivybm.com/api/platforms/instagram/oauth/callback`。Instagram 配置独立于 Meta/Facebook，不得混填 App ID、Secret 或回调；Secret 只注入 app，不注入 migrate / worker。

AI 管理由 Payload 后台的 **AI Management** 菜单完成，顺序是：

1. 新建 `AI Providers`：选择 `openai-compatible`、填写包含 API 版本前缀的 HTTPS 端点（如 `https://api.openai.com/v1`）和 API key。key 是只写字段，保存后只显示“已配置”，不能读回。
2. 新建 `AI Model Profiles`：为文本或向量能力选择供应商，填写供应商模型 ID、超时、最大输出 token；文本模型还可设置 temperature、top-p 和是否思考 / effort，向量模型必须填写固定 dimensions。供应商实际返回的模型 ID 或维度不一致时，请求会失败关闭，避免混用不同向量空间。
3. 新建 `AI Usage Routes`：把稳定业务场景绑定到模型，例如 `chat.reply`（文本）和 `knowledge.embedding`（向量）。下一次请求即采用新配置；路由、模型或供应商被停用时会安全转人工，不会静默使用旧密钥。

升级到要求固定向量空间的版本前，必须先在旧版后台为每个**启用的 embedding route**填写并核对供应商真实输出 dimensions。`20260721_105212_task8_index_owner_recovery` 会在发现缺失、非整数、越界 dimensions 或错误 profile capability 时中止 migration，并列出受影响的 usage key；不得通过猜测或自动填充维度绕过此门槛。补齐后重新执行 migration。此 migration 会把历史遗留的 `processing` 知识文档置为 `failed`，因此发布前先停止旧 worker、等待或中止正在执行的知识索引；新 worker 启动后由 admin 在知识索引入口重试对应 dead job，避免旧进程在 schema 切换窗口继续写入。

`AI Usage Logs` 只记录成功模型调用的模型、供应商、request ID、token、耗时和预估美元成本，不保存 prompt、回复正文或密钥。用量落库失败不会重放已成功的模型调用，也不会把已成功的回答伪装为供应商失败；需在日志中排查该独立运维错误。

旧的 `AI_PROVIDER_BASE_URL`、`AI_PROVIDER_API_KEY`、`AI_TEXT_MODEL` 和 `AI_EMBEDDING_MODEL` 是可选的启动期后备配置：仅当某个业务场景在 CMS 中**不存在**路由时才使用。端点和 API key 必须一起填写，再按需填写文本和/或向量模型 ID；使用 `AI_EMBEDDING_MODEL` 时还必须填写与供应商实际输出一致的 `AI_EMBEDDING_DIMENSIONS`。全部留空即可完全由 CMS 管理。`AI_REASONING_ENABLED` / `AI_REASONING_EFFORT` 只控制这个旧后备文本模型，默认关闭；CMS 模型配置优先。向量请求不会携带 reasoning。

## 1Panel 手动发布

### 发布前 SQL 与媒体备份

本项目不要求云硬盘快照，也不删除任何数据库、媒体卷、图片或客户文件。每次执行 production migration 前必须进入维护窗口：先拉取新镜像，再停止 `app` 与 `worker`，让官网和 Portal 写入口暂时不可用；确认服务端不再接受后台写入后，执行仓库提供的 fail-closed 备份脚本。

```bash
set -euo pipefail
umask 077
./scripts/preflight-production.sh .env
./scripts/production-compose.sh .env pull
./scripts/production-compose.sh .env stop app worker
backup_dir="$(./scripts/backup-production.sh .env)"
printf 'Backup created at %s\n' "$backup_dir"
```

备份脚本会在 `app` 或 `worker` 仍运行时直接失败；使用临时文件、原子目录落盘、目录 `700`、文件 `600`，并验证 `pg_restore --list`、媒体 tar 可读性和 `sha256sum -c`。备份目录必须保留到本次发布 smoke 和回滚窗口结束。

生成后必须在迁移前复制到独立受控的离机位置。可以使用已挂载的受控外部存储，或通过 1Panel 的 HTTPS 文件下载到受控运维工作站；不得把 `/opt/ivybm/.release-backups` 本身当作离机备份，也不得只复制到同一块系统盘。若使用外部挂载目录，复制后执行：

```bash
offsite_dir="/mnt/ivybm-offsite/$(basename "$backup_dir")"
mkdir -p "$offsite_dir"
cp -a "$backup_dir/." "$offsite_dir/"
chmod 700 "$offsite_dir"
chmod 600 "$offsite_dir"/*
./scripts/verify-production-backup.sh .env "$backup_dir" "$offsite_dir"
```

如果离机复制或验证失败，停止发布并恢复旧容器：

```bash
./scripts/production-compose.sh .env start app worker
```

不得继续 migration。离机副本须完成一次隔离数据库 restore rehearsal。仓库脚本会使用固定 pgvector 镜像启动临时数据库，不发布端口、不挂载 production volume：

```bash
./scripts/restore-production-backup-check.sh "$offsite_dir"
```

脚本执行 `pg_restore --exit-on-error` 并读取 `media.tar.gz`；验证结果与 `SHA256SUMS` 一并保留。restore rehearsal 不得写入 production 数据库。

备份、离机复制、验证或 restore rehearsal 任一步失败，都不得继续 migration；按上面的命令启动旧版 `app` / `worker` 并保留旧镜像引用。migration 失败时先保持服务停止，保留 migration 日志和备份证据，由负责人根据隔离 restore 结果决定恢复或修复；不得执行未经批准的 `migration down`，也不得把镜像回滚当作数据库回滚。

在 1Panel Compose 页面选择当前部署目录的 Compose 文件，并使用生产 `.env`。每次发布按以下顺序执行；命令行示例可通过 1Panel 终端或 Lighthouse MCP 执行：

```bash
./scripts/preflight-production.sh .env
./scripts/production-compose.sh .env config --quiet
./scripts/production-compose.sh .env up -d db
./scripts/production-compose.sh .env up --exit-code-from migrate migrate
./scripts/production-compose.sh .env up -d --wait --wait-timeout 120 app worker
./scripts/smoke-test.sh https://ivybm.com
```

`preflight-production.sh` 会拒绝调用 shell 中已导出的 release 变量，并通过 `production-compose.sh` 在清洁环境中解析最终 Compose JSON，确保 app 的 Portal flags、publishing kill switch 和镜像 tag/digest 与 `.env` 同源。`config --quiet` 只验证 Compose，不会将插值后的 secret 输出到终端。`--exit-code-from migrate` 会把 migration 失败作为发布失败返回；`--wait` 会等待 app / worker 健康后才进入 smoke test，smoke test 还会为冷启动重试 30 次、间隔 3 秒。`/admin` smoke 接受现有 200 登录入口，或仅接受同站 `/admin/login` / `/admin/create-first-user` 的 3xx，不接受外部跳转。

每次发布要一起变更 `IMAGE_TAG`、`APP_VERSION`、runtime digest 和 worker digest，直接从同一次 workflow summary 复制。不要只写 Git SHA tag：tag 可被覆盖，digest 才锁定实际镜像。不要执行 `docker compose down --volumes`，也不要让 1Panel 选择“重新构建镜像”。生产 Compose 的 `app` 只监听 `127.0.0.1`，PostgreSQL 和 worker 没有宿主机端口。

## 验证与回滚

发布成功至少满足：

- 1Panel 显示 `db`、`app`、`worker` 健康；`migrate` 一次性成功退出；
- `https://ivybm.com/api/health/live` 与 `/api/health/ready` 返回 200；
- `https://ivybm.com/en` 与 `/ar` 返回 200；
- OpenResty 是唯一公网应用入口。

如应用异常，保留当前和上一版本完整的 tag + digest 对。将 `.env` 同时改回上一版本的 `IMAGE_TAG`、`APP_VERSION`、runtime digest 和 worker digest，依次重新执行 preflight、`pull`、`up -d --wait` 和 smoke test；只有在 migration 已确认成功且无需数据库恢复时才跳过重复 migration。不得运行 migration down；无备份阶段不能把镜像回滚误认为数据库回滚。

GitHub 免费私有仓库当前没有服务端 branch protection；CI 成功表示该提交通过既定门禁，不代替受限写权限、PR review 与本地 pre-push hook。
