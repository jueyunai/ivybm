## 1. 决策目的与优先级

项目已完成官网、Payload 控制平面、`/dashboard` Portal V1 和多项领域能力，但客户可实际验收的跨模块闭环仍未全部完成。本阶段停止继续追求横向工程完备性，改为用 7–10 个工作日集中完成真实业务联调、客户演示和上线验收。

本文件是当前冲刺的唯一执行基线。它不删除历史需求、ADR 或实施记录；当以下文档中的排期、完成定义、测试范围、发布方式或备份要求与本文件冲突时，以本文件为准：

- `docs/requirements/一期需求说明文档.md`
- `docs/plans/2026-07-16-一期开发实施计划.md`
- `docs/plans/2026-07-29-modular-admin-portal-implementation.md`
- `docs/architecture/adr/0004-modular-admin-portal.md`

安全底线、数据模型所有权、共享结构 Review、production 人工审批和禁止提交密钥/客户资料的规则继续有效。

## 2. 已确认的产品与架构口径

### 2.1 `/dashboard` 是唯一客户后台

Payload `/admin` 的选型验证已经失败：其 Collection 导向的信息架构、跨页操作和交互体验不适合作为客户日常运营界面，不能用于一期客户交付或验收。

- `/dashboard` 是唯一客户后台和培训入口；
- `/admin` 仅保留给受限内部维护人员，不进入客户导航，不作为缺失 Portal 功能的回退；
- Payload CMS、Auth、RBAC、Collections、migration 和 PostgreSQL 继续作为唯一后端控制平面；
- Portal V1 已完成的十个模块保留，但冲刺期不再新增模块、通用框架或设计系统能力；
- 只修复阻断四条 MVP 闭环或客户 UAT 的 Portal 问题。

### 2.2 三平台发布是“用户触发的一键 API 发布”

Facebook、Instagram、LinkedIn 的一期目标统一为：

```text
AI 工作台生成内容
  -> 人工审核并确认平台
  -> 用户点击一次“发布”
  -> 服务端按所选平台调用官方发布 API
  -> 分别返回平台发布结果和内容 ID / URL
```

明确边界：

- 不是无人值守、定时或按计划自动发布；
- 不是复制文案、下载图片后到社媒官网人工粘贴；
- 浏览器不得直接调用平台 SDK 或读取 token；
- 选择多个平台时分别调用、分别记录结果，一个平台失败不得覆盖其他平台结果；
- `accepted`、`published`、`failed`、`delivery_unknown` 必须诚实区分；
- 同一次用户操作使用稳定幂等键，结果未知时停止自动重发，由用户核对平台状态后决定下一步；
- 冲刺期不建设通用补偿中心、定时调度、无人值守重试、复杂回调编排或跨平台原子事务。

软件演示验收需要在真实受控测试账号或官方可用测试环境中，至少证明每个已获权限的平台由后台按钮发起 API 发布并取得平台内容 ID / URL。若某平台因客户账号、App Review、地区或官方权限阻塞，只能标记为 `conditional` / `blocked` 并提交 fixture、配置说明和阻塞证据；不得用人工复制粘贴冒充 API 发布完成。

### 2.3 备份改为按需手动执行

一期不建设每日自动数据库或媒体备份，也不承诺自动 RPO / RTO。保留并复用现有手动备份脚本，在以下场景执行：

- production migration 前；
- 批量导入或替换正式内容、媒体前；
- 可能改变业务数据或回滚边界的高风险上线前；
- 客户或项目负责人要求阶段快照时。

普通代码发布、文案调整和无数据结构变化的修复不强制重复备份。每次实际手动备份需记录时间、数据库/媒体范围、校验结果和存放位置；不得把备份提交到 Git。

## 3. 本阶段四条必须真实跑通的 MVP 闭环

### P0-A：官网询盘到飞书

```text
英文/阿语官网表单 -> Leads -> 飞书客户表 -> 新线索/高意向提醒
```

验收证据：真实表单提交、Portal Lead、飞书记录和通知使用同一 request/lead 关联标识，重复提交不产生重复客户。

### P0-B：官网 AI 客服到人工跟进

```text
官网 ChatWidget -> 正式知识与真实 AI provider -> 2–3 轮初筛
  -> 人工接管 -> Lead -> 飞书摘要/提醒
```

验收证据：英文和阿语各至少一个真实场景；高风险问题能转人工；AI/知识不可用时给出可恢复路径，不伪造回答成功。

### P0-C：Portal CMS 到公开官网

```text
/dashboard 官网内容 -> 新建/编辑/发布 -> 英文/阿语公开页面更新
```

验收证据：产品、案例或文章至少各选择一个代表场景，验证保存、发布、公开读取和移动端/RTL 基本可用。`/admin` 不作为客户操作步骤。

### P0-D：AI 内容到三平台一键 API 发布

```text
AI 生成 -> 人工审核 -> 用户点击发布
  -> Facebook / Instagram / LinkedIn 官方 API
  -> 每个平台独立结果、内容 ID / URL 和发布记录
```

验收证据：已获权限的平台使用受控真实账号完成 API 发布；外部权限未满足的平台提供阻塞证据，不以 fake、`available` 状态或人工复制粘贴代替。

## 5. 开发、测试、Review 与 PR 规则

### 5.1 工作优先级

1. 真实环境闭环与外部账号联调；
2. 阻断闭环的 P0 缺陷；
3. 客户 UAT 中影响使用的问题；
4. 已明确承诺的三平台用户触发 API 发布；
5. 其他工作全部排到验收后。

每名开发者同时最多推进一个功能 PR。发现新的工作量超过 1 个工作日，必须先说明它替换哪个既有范围或如何影响日期，不能静默加入冲刺。

### 5.2 测试

开发 checkpoint 只运行与变更直接相关的 lint、typecheck、unit、contract 或 integration 测试。不得为了测试数量重复跑全量回归。

转 Ready、合并或 production 发布仍遵守仓库现有 CI；最终验收重点是四条真实闭环，而不是测试文件数。发布前只保留少量关键 E2E：

- 官网访问和真实询盘；
- AI 对话、接管和 Lead/飞书联动；
- Portal CMS 发布到官网；
- 内容审核和三平台 API 发布；
- 登录、权限和 production smoke。

### 5.3 Review

以下改动继续强制另一名开发者 Review：

- migration、`src/payload.config.ts` 和共享 Collection；
- 跨人 TypeScript contract / schema / 状态枚举；
- Auth/RBAC、凭据、Webhook、真实平台 API 和外部副作用；
- production 发布与回滚边界。

普通自有页面、样式、文案和不影响跨模块契约的修复，由负责人完成定向验证和完整 diff 自检后处理。Review 应一次性集中反馈，避免同一小改动多轮零散复审。

## 9. 风险预警与升级阈值

- 客户正式资料或账号权限缺失超过 1 个工作日：标红并由负责人向客户升级，不用新增工程工作填充等待时间；
- 平台权限/App Review 阻塞：保持 `conditional` / `blocked`，提交证据，不虚报 API 发布完成；
- CI 问题累计超过 2 小时：停止优化 CI，只修复直接阻断当前业务 PR 的最小问题；
- Review 等待超过半个工作日：安排同步 Review，集中给出结论；
- 新需求预计超过 1 个工作日：必须交换范围或调整日期；
- 任何一周没有新增真实闭环证据：项目状态直接标记为延期风险，不以代码、测试或文档数量抵消。

## 10. MVP 完成定义

一期进入客户验收必须同时满足：

1. `/dashboard` 能完成客户日常范围内的官网内容、会话、线索、知识和内容审核任务；
2. P0-A、P0-B、P0-C 在 production 或等价真实环境有验收证据；
3. P0-D 对已获权限的平台完成用户点击后的真实官方 API 发布，并记录平台内容 ID / URL；
4. 未获外部权限的平台有明确阻塞证据，不以 fake、人工复制粘贴或错误 `available` 状态代替；
5. production 变更按本文件触发条件完成必要的手动备份、smoke 和回滚准备；
6. 客户完成基础培训，UAT 无未处理 P0 阻塞项；
7. 所有非阻断问题进入后续清单，不继续阻塞 MVP 上线。
