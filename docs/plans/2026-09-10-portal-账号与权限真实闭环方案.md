## 1. 目标

使用 Payload 3.86.0 原生 username 认证实现普通账号登录，并为实际 Portal 的 9 个模块提供 `view/edit` 权限点。权限必须持久化、进入会话并在服务端强制执行，不能只隐藏前端按钮。

历史 `4700da6` 只作为布局参考。禁止把普通账号写入 `email`，禁止无 migration 增加 `permissions`，禁止让后端静默丢弃权限。

## 2. 数据与类型契约

Payload Auth 配置：

```typescript
auth: {
  loginWithUsername: {
    allowEmailLogin: false,
    requireEmail: false,
    requireUsername: true,
  },
  // 保留当前 cookies、lockTime、maxLoginAttempts、tokenExpiration、useSessions
}
```

权限类型：

```typescript
export type PermissionModuleId =
  | 'conversations'
  | 'leads'
  | 'website-content'
  | 'media'
  | 'content-studio'
  | 'knowledge'
  | 'platforms'
  | 'operations'
  | 'settings'

export interface ModulePermission {
  view: boolean
  edit: boolean
}

export type PortalUserPermissions = Record<PermissionModuleId, ModulePermission>

export interface PortalTeamMemberDTO {
  id: number | string
  username: string
  role: 'admin' | 'operator' | 'sales'
  permissions: PortalUserPermissions
  status: 'normal' | 'security_locked' | 'manually_locked'
  lockedUntil: string | null
  createdAt: string
  updatedAt: string
}
```

权限键必须直接复用当前 Portal Registry 的稳定模块 ID，禁止为权限系统另造 `content` / `contentStudio` 别名或修改现有 manifest slug。规则：`edit=true` 必须同时归一化为 `view=true`；`view=false` 必须同时归一化为 `edit=false`。预设模板只负责生成默认矩阵，保存后以持久化权限为准。旧用户 migration 按原 `role` 写入对应预设，避免升级后权限漂移。

## 4. API 契约

```typescript
export interface CreateTeamMemberInput {
  username: string
  password: string
  role: PortalTeamMemberRole
  permissions: PortalUserPermissions
}

export interface UpdateTeamMemberInput {
  username?: string
  role?: PortalTeamMemberRole
  permissions?: PortalUserPermissions
  updatedAt: string
}
```

重置个人密码仍保留当前密码与新密码确认；只有管理员创建成员时使用单项临时密码。响应 DTO 不得包含 password、salt、hash、token 或 session。

## 5. 明确不做

- 不允许邮箱登录，不把 username 映射到 email。
- 不实现任意自定义权限字符串，只允许冻结的 9 模块 x 2 动作。
- 不通过前端隐藏代替服务端 403。
- 不改变 sales 的资源归属过滤、平台 token 安全、知识库 admin-only 配置等既有更严格约束。
- 不 push、不创建 PR、不部署 production，除非用户另行授权。
