- 状态：已按代码核验修订（第 4 版），待实现与验收

- 适用范围：MVP 本地 / CI 自动化、发布前受控 canary、客户验收证据
- 上位基线：[MVP 范围冻结与交付冲刺](./2026-08-10-MVP范围冻结与交付冲刺.md)

> 第 4 版修订依据：在第 3 版基础上拆分 FB-PUB-05 的既有绿色授权守卫与 revision-only known-red，并明确 AI stub 在本地 development 与 CI production 环境的不同接入前提。

## 1. 目的与范围

本文件把当前 MVP 的关键业务闭环转换为可执行测试用例，目标不是增加测试数量，而是证明用户可实际完成业务、外部副作用不会重复、系统不会把 fake 或未知结果伪报为成功。

当前首轮社媒验证顺序确认为：

- 消息入站：Facebook Messenger；
- 内容发布：Facebook Page 单图图文；
- Instagram、LinkedIn 不进入首轮自动化与真实 canary 的完成门槛；仍按上位冲刺基线记录为后续接入或 `conditional` / `blocked`，必须保留权限、配置和阻塞证据，不得显示为 `available`；
- 本文件不把 Facebook 首轮验证解释为三平台范围已经全部完成，也不以人工复制粘贴替代官方 API 发布。

## 2. 测试架构与真实性边界

### 2.1 推荐架构

本地 / CI 运行以下真实组件：

- Chromium 浏览器、Next.js、Payload、PostgreSQL；
- Portal / 官网真实路由与服务端 Auth / RBAC；
- 真实业务 Collection、数据库事务、Jobs 队列、领域状态机；
- 真实 Webhook HMAC 验签、幂等键、worker handler、authority / fence / CAS；
- 真实 Portal 读模型和最终用户可见状态。

只替换最后一道外部网络出口。但**注入点按进程分成两半，不是统一的一层 port**，这决定了各闭环的可实现顺序：

| 外部出口 | 调用发生在 | 现状 | 可否在不改生产代码的前提下替换 |
| --- | --- | --- | --- |
| Meta 会话发送 | worker（`worker.ts` 注册 delivery handler） | `fakeConversationOutboundPort.ts` 已在 `src` 内 | 可以：测试进程装配 worker 时注入 |
| Meta 发布 | worker（publication handler） | `fakePublishingPort.ts` 已在 `src` 内 | 可以：同上 |
| 飞书 | worker（lead sync / notify handler） | 已有 fake client 与契约测试 | 可以：同上 |
| AI（网站客服） | **server 进程，请求内同步** | `runtime.ts:34` 创建真实 responder；responder 通过 `resolveAiGateway` 读取 CMS / 环境中的 OpenAI-compatible provider | **可以**：测试 fixture 将 provider `baseURL` 指向受控 stub；CI production 模式需使用受信任 HTTPS stub，或新增经 Review 的 loopback 豁免（当前不存在，见 §8 步骤 13）；不需要替换 `runtime.ts` |
| AI（平台会话回复） | worker（`worker.ts:197`，受 `conversationsEnabled` 门控） | 同 worker 侧 | 可以 |

补充事实，避免实现时走错路：

- Meta Graph origin 是硬编码模块常量（`src/modules/platforms/meta/publishingOutbound.ts:31`、`conversationOutbound.ts:53`），**没有 base URL 注入口**；唯一 seam 是 `fetch` 参数（`publishingOutbound.ts:211`、`conversationOutbound.ts:152`）。因此"把 base URL 指向本地 stub 从而在网络层面保证到不了 Meta"这条路不存在。
- 服务端 fake AI 的可行实现是本地 OpenAI-compatible stub（`src/modules/ai/providers/` 目前只有 `openaiCompatible.ts`）。通过 AI Provider 的 `baseURL` 配置即可让 server 进程请求 stub；production 模式下必须满足 HTTPS 校验，不能使用真实付费 AI。

Playwright 不使用 `page.route()` 模拟 IVYBM 内部业务 API。复杂 provider 故障、并发、lease 和进程死亡注入优先放在 integration；浏览器 E2E 负责验证用户操作、真实数据库结果、队列结果和 Portal 展示。测试实现沿用仓库现有的 `getByRole` / `getByLabel` 等可访问语义定位。

### 2.2 发布前真实 canary

真实 canary 使用受控账号、实际 app / worker 和官方 API，验证本地 fake 无法证明的内容：

- Meta App、Page task、Webhook subscription 和 App Review；
- Page token、`pages_manage_posts` 和 Messenger 发送权限；
- 公开媒体能被 Meta 读取；
- 官方返回内容 ID / URL 与 Facebook 页面实际内容一致；
- 真实环境的 Worker wiring、网络和凭据读取。

**当前基础设施只有一台线上服务器，因此 canary 就是生产，不存在"等价真实环境"这个选项。** 由此以下几条不是可选项：

- 只使用受控测试账号与合成内容，禁止真实客户资料；
- 每条 canary 必须留脱敏关联 ID、时间与执行人；
- Facebook 发布 canary 会在真实 Page 留下内容，是否删除由测试负责人在 Facebook 页面人工确认并记录，禁止自动删除、禁止自动重跑；
- canary 执行前需 jueyunai 明确批准。

普通 CI 禁止调用真实 Meta、飞书或付费 AI，避免误发内容、消耗额度、外部波动和凭据泄漏。

### 2.3 明确不采用

- 不把现有 UI mock 用例视为真实业务闭环（`tests/e2e/chat-handoff.spec.ts` 与 `tests/e2e/admin-portal-conversations.spec.ts` 目前都用 `page.route()` mock 内部业务 API，保留其 UI 契约价值，但不作为闭环证据）；
- 不为测试引入通用外部平台模拟框架或修改冻结的 CI policy；
- 不在 `delivery_unknown`、真实账号未授权或 fake 结果下标记平台已发布 / 已发送；
- 不通过伪造邮箱绕过社媒身份到 Lead 联系渠道的产品缺口。

## 3. 测试数据与清理规则

- 测试实体名称沿用仓库既有 `e2e-` 前缀惯例（现有用例使用 `portal-e2e-space`、`portal-conversation-e2e`、`e2e-member-001`），Facebook 相关用例统一使用 `e2e-fb-` 前缀，便于前缀扫描清理；不引入新的后缀约定，不设无依据的长度上限，仅需满足对应字段的 `maxLength`；
- 邮箱使用 `example.invalid`，Page / sender / message ID 使用合成数字或明确的测试 ID；
- 不使用真实客户姓名、原始询盘、电话、token、合同、报价或媒体；
- 每个用例持有唯一 correlation ID，并贯穿页面响应、Conversation、Message、Lead、Handoff、Job、PublishJob、PublishLog 和 fake provider 请求；
- 用例在 `finally` 中按依赖顺序清理测试账号、映射、内容、媒体、会话、消息、Lead、Handoff、Jobs、command receipt 和审计记录；
- 失败分支也必须清理；清理失败应使测试失败，不得静默遗留共享测试数据。

### 4.6 AI 内容审核到 Facebook Page 图文发布

## 9. 实施与验收门禁

每条 P0 用例的验收记录至少包含：

- base / head SHA 和运行环境；
- 测试用例 ID、开始 / 结束时间、执行人；
